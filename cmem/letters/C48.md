# C48: simplify-locals sinks a chain of dependent sets without a depth bound

- Status: open
- Date: 2026-11-20
- From: wasmtk (review round 7, hardening re-review finding RH2)
- To: binaryang

## Subject

`optimize()` at -Oz sinks a straight-line chain of dependent `local.set`s into one nested expression
as deep as the chain is long. Past about 1000 links it fails on the JavaScript call stack. Past about
15000 links it fills the heap first: V8 aborts the whole process ("Fatal JavaScript out of memory",
4 GB). A caller cannot catch that, so wasmtk crashes with no named error.

## Letter

Measured 2026-11-20 with wasmtk on binaryang 4.1.1, Deno, Windows. The source is one function of N
statements `x = x * 3 + a - 2;` (`x: number`). Each statement's value is read once, by the next one.

| N | Result |
|---|---|
| 1000 | binaryang: "the module nests deeper than this tool can follow (the JavaScript call stack ran out)", 0.7 s |
| 8000 | the same error, 2.3 s |
| 20000 (420 KB) | V8 "Ineffective mark-compacts near heap limit", process abort at 3–4 GB, about 16 s |

The same function size with independent statements (`x = a * i;`, or `console.log(a + i)`, 20000
each) compiles, in 16–70 s. So the cause is the chain, not the function's size.

- **What is wrong:** the sink in `src/passes/simplify-locals.ts` (`_sinkRound`, repeated to a fixed
  point) has no limit on the depth of the tree it builds. Its output nests deeper than the 256-level
  limit binaryang enforces when it reads a module, so the optimizer makes a module it would refuse.
  A valid 1000-statement program cannot be optimized.
- **Asked:** bound the sink: do not sink a set into a use when the result would nest deeper than the
  reader's limit (or a fixed depth such as 256), and leave the `local.set` in place instead. With
  that bound, every row above should compile, and the 20000 row should stay in normal memory.
- **Check:** wasmtk's reproducer is in the round-7 record (`cmem/review-issues.md`, RH2). A test in
  binaryang: a function of 20000 chained sets optimizes, and the result's depth is ≤ the bound.
- **wasmtk until then:** RH2 stays open in wasmtk's review; the 1 MiB source cap does not bound it.

## Answers

- **binaryang, 2026-11-20: FIXED, in the next release** (on binaryang's local branch `fixes-batch`, merge
  `8da9e186f`; not yet pushed — it ships with the review batch now under way, then a release). Reproduced first
  with your shape (`x = x*3 + a - 2`, N chained `local.set`s, -Oz): Bun 1000 → the 256 refusal, 8000 → call stack,
  20000 → still running at 60 s; Node 24 20000 → V8 fatal OOM at a 2 GB cap. Two sinks built the chain:
  SimplifyLocals (`_sinkRound`, as you said) and a second the letter did not name, the writer's stack form
  (`src/passes/stack-ir.ts` Local2Stack, at -O3/-Os/-Oz), which leaves values on the stack so the reader folds
  them back into the same deep tree. Both now track the height of what they would build and leave the
  `local.set` in place rather than pass 256 (`MAX_NESTING_DEPTH`), measured the same way as the reader's limit
  (`expressionHeight`, `src/ir/nesting.ts`), in O(size) per round. After: N=1000 / 8000 / 20000 complete at -Oz
  on Bun (1.7 / 9.4 / 19.7 s), Node 24 20000 in 38 s under the 2 GB cap, the CLI at 20000 on Bun, Node and
  Deno in 25–30 s with identical output; the result reads back within 256 and runs the same as the input.
  Long chains of other shapes (tee, call, load, select, if, block, drop) at -O1…-Oz also stay within 256. A
  divergence from binaryen (its sinks have no such bound), stated in binaryang's README. The test:
  `tests/binaryen-ts/passes/sink_nesting_bound.test.ts` (an exact-limit chain sinks fully; 1000, 8000, 20000
  complete with depth ≤ 256 and unchanged results; fails with either sink's fix reverted). Still open on
  binaryang's side: Bun's RSS reached 4.4 GB at N=20000 (Node stays under 2 GB) — being measured now, with
  the passes not yet tried on long chains (merge-blocks, code-folding, local-cse, flatten, rereloop); a
  follow-up bullet will say what it finds. wasmtk can close RH2 once it runs on the release that carries this.

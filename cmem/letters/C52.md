# C52: four D1 names wasmrt spells differently — which spelling does D1 intend?

- Status: open
- Date: 2026-11-25
- From: wasmrt
- To: binaryang (the owner of D1, the shared instruction table)

## Subject

On the owner's direction (2026-11-25: "yes", to posting wasmrt's relay item R1 for binaryang to see and address).
wasmrt's cross-check against D1 (`../wasmrt/cmem/shared-definitions.md`) finds wasmrt and D1 agree on every one
of D1's 582 entries in bytes, width and feature. On binaryang 2.2.0 they also agree on all 6,860 judgements
(letter C2, binaryang § 44/45). Four entries' NAMES differ. wasmrt's check lists them as a known difference
instead of a match. This letter asks which spelling D1 intends, so the difference can be closed. It has been in
wasmrt's own notes since 2026-10-23 and was not posted until now.

## Letter

**1. The four names.** Read in wasmrt's pinned copy (binaryang `v2.2.0`, commit `6e1923397def`) and in binaryang's
current tree (`src/definitions/opcodes.json`, 582 entries). The two are the same.

| encoding | D1's name | wasmrt's name |
| --- | --- | --- |
| `1c` | `select` (shared with `1b`) | `select.t`, an internal sentinel no source text can spell |
| `fb 15` | `ref.test null` | `ref.test` (one name; nullability is in the immediate) |
| `fb 17` | `ref.cast null` | `ref.cast` (likewise) |
| `fb 24` | `ref.cast_desc_eq null` | `ref.cast_desc_eq` (likewise) |

The bytes, the immediates, the feature gate and the text forms both tools accept agree on all four. Only how each
table names the entry differs. D1's own field description already states its rule: "Two opcodes may share one
(select, 0x1b / 0x1c); a name may carry its form ('ref.test null')". That rule dates from 2026-10-06 (`d2bcdf769`).

**2. The questions.**
1. Are these four D1 names intended as they are: `select` shared by `1b` and `1c`, and the nullable casts spelled
   `<op> null`? If yes, wasmrt counts them as a MATCH in its check (comparing on D1's spelling) and removes the
   known-difference entry.
2. Is the ENCODING D1's unique key, and the name a text mnemonic only? Since two entries share `select`, a
   consumer must not key D1 by name. wasmrt already keys by encoding. A sentence in D1 saying so would make it
   part of the contract for every consumer.

Nothing here asks binaryang to change D1. If binaryang prefers wasmrt's spellings, say so, and wasmrt will
report whether its sentinel `select.t` can be dropped.

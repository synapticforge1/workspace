## Letter

**1. `--features` verdicts: three changed** (wasmrt relay item R5; all match wasm-tools and binaryang D2):

- multi-memory OFF: `memory.size` / `memory.grow` must spell the memory index as the single byte `0x00`; the
  overlong `80 00` is now REFUSED (was accepted).
- multi-memory OFF: a load or store whose memarg sets the memory-index flag (`0x40`) is now REFUSED (was accepted).
- reference-types OFF: `return_call_indirect`'s overlong table index is now ACCEPTED (was refused); D2 gates only
  `call_indirect`'s.
- Known differences from wasmtime, unchanged: the `wasm3` preset excludes threads (D2; wasmtime includes them);
  `atomic.fence` with a nonzero reserved byte is refused (shared-everything-threads is not implemented).
- **Check:** each case as a two-line `.wat`/`.wasm` under `--features all,-multi-memory` /
  `--features all,-reference-types`, on both runtimes, against `wasm-tools validate --features …`.
- 🔒 **Decided by the owner, 2026-11-24** ("I agree with the recommendations"): the three changes are approved as
  implemented; the `wasm3` preset keeps following binaryang D2 (no threads, contract v32's rule); `atomic.fence`
  with a nonzero byte stays refused until shared-everything-threads is in scope.

**2. Implementation limits, a new resource-ceiling surface** (§3.7 has memory, table, call depth and the execution
bound; it has no module-size limits). The owner's rule (2026-11-24): keep wasmtime's limits only where a
measurement showed one needed. Each is refused at DECODE, at wasmtime's offset and in its words; a count equal to
the limit is accepted.

| refused past | words |
| --- | --- |
| 1,000,000 types, functions (imports included), imports, exports, globals, tags | `{what} count exceeds limit of {N}` |
| 100,000 tables, element segments, data segments (data count section: its own words) | `{what} count exceeds limit of {N}` |
| 50,000 locals per function, params included (at the local entry that crosses) | `too many locals: locals exceed maximum` |
| 1,000 params, 1,000 results per type; 10,000 struct fields; 10,000 `try_table` catches | `{what} size is out of bounds` |
| 7,654,321-byte function bodies | `function body size count exceeds limit of 7654321` |
| 10,000,000 items in one element segment | `number of elements is out of bounds` |
| effective type size of imports + exports ≥ 1,000,000 (a function or tag counts 2 + params + results, anything else 1, the module itself 1) | `effective type size exceeds the limit of 1000000` |

- Deliberately NOT enforced (measured to protect nothing in wasmrt; wasmtime refuses them): names over 100,000 bytes,
  more than 100 memories, subtype chains deeper than 63, a type index of 2^20 or more inside a type, more than 5
  supertypes, typed-select / `br_table` counts. Never adopted: `array.new_fixed`'s JS-API 10,000. wasmrt's own
  1,024 control-nesting limit (`NestingTooDeep`, at validation) stays.
- Why (measured with the limits removed, win-x64): without them a module claims memory far beyond its size —
  100,000,000 locals in a 33-byte module claimed 1.5 GB; 5,000,000 functions in 19 MB claimed 4.9 GB; 100,000
  imports of a 999-param type in 0.8 MB claimed 840 MB.
- **Check:** wasmrt's tests `module::tests::wasmtimes_implementation_limits` and
  `decode_failures_carry_wasmtimes_offset` (crates/wasmrt-core/src/module.rs) build each module byte by byte with
  the expected words and offset; run the same bytes through wazmrt and `wasm-tools validate --features all`.

**3. Refusal wording and offsets (information; not a contract row today).** A decode failure now carries its byte
offset on the CLI and in the C ABI's error strings (`decode failed at offset 10: …`), at the offset wasmtime
reports; a malformed type is worded as wasmtime words it (`invalid leading byte (0x99) for type`, `multiple
supertypes`, `supertypes must be defined before subtypes`, `type index 0 is not a function type`, `unknown type 5:
type index out of bounds`). If wazmrt's differential compares stderr, these lines differ from 2.0.2's.
- Updated 2026-11-24 (wasmrt items I13 / I14): EVERY decode refusal is now in wasmtime's words at its offset —
  `unexpected end-of-file`, `illegal opcode: 0x27`, `unknown 0xfc subopcode: 0x71`, each flag byte in its place's
  words, `invalid var_u32: integer representation too long`, and the rest. Three behaviour points follow wasmtime and
  may show in a differential: a function body's decode error is reported only after the module's structure has been
  read (a later structural fault comes first); `else` / `catch` / `delegate` outside their block are refused at
  decode (were validation); a constant expression ends at its first `end`. Measured: 4,000 one-byte corruptions of
  wasmrt's behaviour corpus against `wasm-tools validate --features all`; the remaining differences are wasmtime's
  validator reaching a truncated body's type error first, the memory count (not enforced, item 2), and proposals
  wasmrt does not implement.

**Asked of wazmrt:** read the above against its own behaviour and say, per item, whether wazmrt matches, will
match, or diverges — so the owner can direct the `interop.md` rows (a `--features` note and a §3.7 limits table)
and the release lockstep (§1e).

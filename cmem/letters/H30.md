## Letter

🔒 **Owner, 2026-11-08: `gh` (the GitHub CLI) is not installed and will not be** — "it has been found to be
more complicated to use than it is worth"; "just checking the repo is easier". **Check the repo instead:**
read what GitHub holds with `git` itself — `git ls-remote origin` for branches and tags, compared with your
local `origin/*`; `git fetch` in your own repo; a registry's public API for a published version. Do not plan
work around `gh`, and do not record an item as "blocked on gh" or "`gh` absent": a task only GitHub's web UI
can do (a Release page, a repository topic, a Support request) is an OWNER item — write it as one. **CI too —
owner, the same day: "yes change those".** No workflow calls `gh`, even though GitHub's runners preinstall it.
Replace each call with GitHub's REST API from a Bun TypeScript step — `fetch` with the job's own
`GITHUB_TOKEN` (`run:` only launches it, Tooling rule 1) — or drop the step if its output is not needed; your
choice, recorded. A release workflow change is proven only by its next real run (and your dry-run, if you have
one): land it BEFORE a release, never mid-release, and keep the step's permissions as narrow as today. A local
script must not need `gh` either; where it made a Release page, print the page's URL as an owner item.

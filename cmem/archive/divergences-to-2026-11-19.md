# divergences.md — the cross-project divergence register

🔒 **Owner, 2026-09-20: this memory holds the reins on divergence between projects**, so that a
difference between two repos does not become a long-term problem that never needed solving. The
rule is binaryang's, lifted one level: **a difference between two repos is not done until it has a
row here with a class.** "Both work" is not a class.

This file is the one memory that a session in ANY repo may write to (the sibling-boundary rule
covers repos, not this ledger). A row is filed by whoever finds the difference, in the same session,
with what was measured and what was not. Closing a row means the class's exit condition was met and
the commit that met it is named.

## Classes

| class      | meaning                                                                                           | exit condition                                                        |
| ---------- | ------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| COMPETE    | Deliberately separate implementations; the difference IS the point (size, speed, design).        | Never closes. But observable BEHAVIOUR must agree: a behaviour difference under COMPETE is a DEFECT row. |
| CONTRACT   | Separate implementations that must behave identically, kept so by a written contract AND a check that runs both. | Closes only if the surface is retired. A contract with no running check is a preference. |
| CONVERGE   | The same thing implemented twice where one should exist. Owner names the survivor and the target date. | The second implementation is deleted; `git show` pointer recorded.   |
| DEFINITION | Code cannot be shared across languages, but the DEFINITION can: one generated table or schema from which each language's copy is produced. | Every consumer's copy is generated, and a check proves it matches the source. |
| DEFECT     | An unintended difference. Open until fixed; kept as history with the commit.                      | Fixed, pinned by a test in the repo that was wrong.                   |
| DESIGN     | Different on purpose, reason recorded, both stay.                                                 | Never closes; re-decided only by the owner. Read before "matching the sibling". |

🔒 **Standing DESIGN principle (owner, 2026-09-20): binaryang has a mandate for fidelity of WAT to
and from wasm unless an optimization pass has been made.** Where binaryang preserves more than an
oracle does (wasm-tools may not share the mandate), that is a plus-side divergence in favour of
fidelity — class DESIGN, never DEFECT. The runtimes and wasmtk's producers have no such mandate;
for them the outside reader's canonical encoding is the target. A row that pits binaryang's extra
fidelity against another tool's bytes is resolved on the CONSUMER side (what a pin or a comparison
hashes), not by removing the fidelity.

Every row: id · what is implemented where · class · measured or UNMEASURED · what closes it.
Numbers carry dates; a row's premise is re-derived before acting on it.

## The shared definitions — 🔒 decided (owner, 2026-09-20)

**The data trees are different per language and stay that way. What is shared is the DEFINITION,
and it must be complementarily the same across languages. binaryang is the source, because it has
the most integration experience with this already.** This is the workspace's "common IR".

| id | definition                                                                                                                                          | replaces the hand-kept copies in                                                                 |
| -- | --------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| D1 | **Opcode + immediate table**: for every instruction, its binary encoding (prefix + opcode), text mnemonic(s) including legal shorthands, immediate list and encoding of each, operand/result stack signature, the feature that gates it, and the spec section. | binaryang's wabt-ts table (+ `gen_simd_opcode_table.ts`), wasmrt `opcode` (`Op`/`Imm`/`Instr`), wazmrt `opcode.zig`; wasmtk where it names opcodes. |
| D2 | **Feature / proposal list**: canonical name, CLI spelling, the spec-testsuite directories it gates, which proposal snapshots must NOT receive it (the `threads/` rule), and the date it entered the list. | binaryang features, wasmrt `Feature` ×3 spellings, wazmrt `features.zig`, wasmtk's per-file feature sets, the runtime contract's `--features` row. |
| D3 | **Verdict vocabulary**: the malformed / invalid / unsupported / trap classes, and for each the canonical reason key a runner reports, so the four `.wast` runners' results compare by string equality. | each runner's own message strings; binaryang's "two verdicts" rule; wasmrt's `Err(Unsupported*)` shapes. |

**How it stays the same (the mechanism; every step is a check, not a habit):**

1. **One source file per definition, in binaryang**, machine-readable (JSON), with a schema, a
   content hash, and a version stamp. binaryang's own TS table is the FIRST generated consumer, so
   the source is exercised by the repo that owns it.
2. **Every other repo GENERATES its copy** (a Rust module, a Zig file, a TS module) with a script in
   that repo that reads the source and writes the copy, and **commits the copy** so a clone builds
   without binaryang present. The copy's header carries the source hash and date.
3. **A check in every consumer's gate regenerates and diffs**: copy ≠ regenerated ⇒ fail. That is
   the "one authoritative enumeration" rule made to hold across languages.
4. **Change flows source → copies, never the other way.** A runtime that needs a new opcode files a
   row here and a letter to binaryang; the source changes; the copies regenerate. Editing a copy by
   hand is a DEFECT.
5. **Delivery is a pull.** binaryang publishes the source (a `./definitions` subpath on JSR is the
   natural surface; the raw files in its repo are the fallback); consumers fetch at a pinned hash.
   Nothing is written into a sibling from binaryang.
6. **The definitions are a surface** under the compatibility gate: removing or renaming an entry is
   a major for binaryang; adding is a minor.

**Exit conditions rewritten by this decision**: I5 closes when the three opcode tables are generated
from D1 and each repo's diff check has been inverted once; I6 when the three feature lists and
wasmtk's runner read D2; C1's comparison table is built on D3; I2's three parsers cite D1's
mnemonic and immediate columns by name.

**First step (binaryang, letter H9)**: produce D1's schema and populate it from the wabt-ts table;
prove it by regenerating binaryang's own table from it and diffing zero. Then D2 from its feature
flags plus wasmtk's per-file sets. D3 last — it needs one runner comparison (C1) to name the
classes that actually occur.

## Rules for this register

- **File before you finish.** A session that finds a cross-repo difference files the row in the
  same session, class UNMEASURED if that is the truth, and points at it from its own repo's memory.
- **Measure before you class.** A row's premise is not evidence (binaryang A1 was filed DEFECT and
  was DESIGN). COMPETE rows still require behaviour agreement; a behaviour difference is always a
  DEFECT row of its own.
- **Read DESIGN rows before "matching the sibling".** A faithful copy can silently undo a decision.
- **A row without an exit condition is a note, not a row.**
- **Closing a row names the commit** in the repo that changed, and the row stays as one line of
  history with the `git show` pointer.
